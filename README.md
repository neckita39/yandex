Задание 1: Реализованы уровни 1, 2

Уровень 1: Module Federation
При выборе паттерна я бы учитывал следующие важные аспекты:
1. Бизнес: какие приоритеты и боли пользователей (долгая первая загрузка, долгий отклик и медленная работа некоторых компонентов), какие сроки для итераций, как часто релизимся
2. Технические: какие фреймворки используются в компании (React, Angular и тд)
3. Человеческие: какие ресурсы доступны, какие хард скиллы у сотрудников

Если необходимо развертывать микрофронты независимо, к каждому фронту есть есть специфичные требования, итерации частые и сотрудники знают различные js фреймворки, то выбор будет в сторону Single SPA

Для остальных случаев Module Federation.

В своем решении я также выберу Module Federation, потому что:
1. Его проще внедрить в общем случае
2. Он соответствует всем достаточным и необходмым условиям в данном случае (функций lazy loading'a пока будет достаточно для быстродействия)

Уровень 2:
Приложение поделено на микрофронтенды согласно бизнес-логике (DDD):

auth - для регистрации и авторизации
profile - для работы с профилем
phtots - для работы с постами
ui - общая ui библиотека, которая используется почти всеми фронтами

host - конфигурация приложения + хедер и футер

По поводу ui. Очевидно, что такой подход создает зависимости других фронтов на этот фронт. Второй вариант - оставить в host. Третий вариант - объединить общие стили в общую библиотеку, но пока я остановился на отдельном микрофронте. Поэтому в конфиг остальные микрофронтов в секцию remotes я добавил фронт ui, и в секции shared указал, что он singleton

Такое разделение мне кажется правильным, потому что в этом случае каждый микрофронт отвечает из свою конкретную бизнес-логику, кроме микрофронта ui, который используется всеми. Возможно, его бы стоило оставить в host, но я хочу, чтобы этот микрофронт занимался только оркестрацией.

каждое приложение имеет такую структуру:
/auth
  /src
    /components					// контролы
    /blocks						// блоки со стилями
    /utils						// утилиты (api,js, ...)
    index.js                 // Точка входа микрофронтенда
  package.json               // Зависимости и скрипты микрофронтенда
  webpack.config.js 		// конфигурация для Module Federation

В каждый микрофронт вынесены его стили и компоненты, которые относятся только к нему, а также вспомогательные файлы из utils

Более подробно содержимое новых микрофронтов можно увидеть в пулл реквесте

Файл auth.js вынесен в auth. Файл api.js распаршен по нужным фронтам, теперь нужные функции лежат в нужном фронте. 

Сделаны наброски по маршрутизации - описаны директивы exposes, remotes, чтобы хост мог обращаться к нужным фронтам.

Контекст я поместил во все микрофронты, которым он нужен.

В файле host/src/App.jsx сделаны наброски по ленивой загрузке остальные фронтов.

Для взаимодействия между фронтами будут использоваться ивенты и shared storage.

Запуск: в каждом приложении необходимо выполнить npm i, npm run start. Можно добавить микрофронты в yaml докера и поднять приложение там.

В левом верхнем углу диаграммы описаны новые потоки. 

Описание:
Монолит разбит на 9 сервисов, согласно их предметной области

1. Управление пользователями - отвечает на авторизацию, регистрацию и пользователь профиля
2. Каталог товаров и услуг - предоставляет операции с товарами, а также показ, фильтрацию и поиск.
3. Обработка заказов - сервис ответственен за обработку заказов
4. Обработка платежей - сервис, котрый создает платежи на основе заказа и решает другие "финансовые" задачи
5. Поддержка клиентов - отдельный сервис, который позволяет клиенту взаимодействовать с ТП
6. Отчетность и аналитика - сервис для построения отчётов
7. Нотификации - сервис для отправки уведомлений
8. Управление апелляциями - для работы с апелляциями.

Каждый сервис дополнительно описан на диаграмме.
